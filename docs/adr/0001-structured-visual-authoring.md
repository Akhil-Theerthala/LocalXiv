# Structured visual authoring with composition freedom

Superseded by [ADR 0002](0002-model-authored-svg-overviews.md). This record remains as the
historical rationale for the former scene-compiler design.

The user reports that custom SVG authoring takes too long or fails across the models they use. The agreed direction is structured authoring that preserves freedom to compose useful, varied visual explanations; the production format is a scene of rows and typed panels.

The agreed boundary gives the agent responsibility for evidence-grounded content, relationships, and relative composition, while application code handles coordinates, text measurement, and connector paths. The agent can compose smaller visual elements within panels as well as arrange the panels. Whole-page templates alone would constrain explanations too much. The implemented elements include flows, parallel branches, linked lanes, concepts with examples, candidate sets, calculations and findings. Rows and relative panel widths control composition; invalid or overfull scenes return concrete corrections to the author.

Visual quality is an explicit requirement: explanations must look simple, clean, attractive, and easy to follow. A valid structured description alone does not satisfy this requirement. Renderer rules include consistent typography and spacing, restrained color with a clear purpose, visible reading order, and connectors that avoid labels. The composition should establish a dominant visual focus and use supporting material only where it helps understanding; panels need not have visible borders or equal dimensions. Overfull compositions should be reorganized or simplified rather than fitted by shrinking labels. Representative rendered examples must establish whether these rules produce the intended appearance before the format is finalized.

The user confirmed that an Overview must remain an overview and should not become crowded. Its scope is orientation to the contribution, essential idea, and main finding with the qualification needed to interpret it. Detailed walkthroughs and secondary results belong in a separately requested Blog; Overview generation must not require or automatically generate a Blog. Do not force a worked example, every architectural layer, or a fixed number of panels into each Overview. Simplification must preserve the relationships and conditions essential to the claims shown.

The user clarified that selecting a single headline idea can oversimplify the explanation. Architecture papers need stage-by-stage flow and the connections between the core operation, parallel composition, and overall system. Survey papers need approach families with small explanations from first principles, rather than an invented shared pipeline. Methodology papers should lead with an example and carry it through the actual operations to their output. These are content requirements that guide composition, not three mandatory page templates. Simplicity should remove clutter while preserving the relationships needed to understand the paper.

A further prototype review established that labels and equations alone can leave beginners unable to follow the process. Each transformation should explain where its input comes from and what its output means. For attention, show token matching, weights and information mixing, and explain that heads learn different projections of every token rather than dividing tokens among heads. Surveys must connect first principles to representative named methods, their priorities and tradeoffs, and the survey's findings. Worked methods must introduce the origin and meaning of numerical terms before displaying arithmetic. Preserve the concise Overview scope through selection and composition.

The existing explanation plan records claims and supporting relationships. The scene format builds on that plan without requiring the model to author low-level geometry. Reduced latency and fewer failed generations are hypotheses to verify with representative papers and the user's models.

The user approved production integration after reviewing the architecture, survey and method examples. Subsequent feedback clarified that the Overview must tell the story of the uploaded paper from beginning to end. Adding relevant method names without connecting them to the argument failed that requirement. The revised survey introduces representative methods through their operations and closes with the survey’s synthesis. Both planning and evidence review explicitly check that narrative.

`papers/overview_scene.py` now validates and compiles structured scenes. The Overview author submits `scene`, never raw HTML/SVG. `HTMLSnapshot.swift` measures label widths in a batch before layout; its existing WebKit checks and static exports remain the final geometry gate. Scene data and generated HTML both persist with the reviewed candidate. Blog authoring retains its existing format and can inspect a saved scene alongside the reviewed Overview as reference.

`papers/overview-examples.json` contains the reviewed compositions as editable data and supplies the locally loaded Overview composition reference. `papers/prototypes/structured_overview.py` is now only a review page that calls the same production compiler. There is no separate prototype renderer to drift from generation. Blog retains its saved-Overview reference behavior.

The selective-evidence implementation adds local orientation, evidence selection, an accepted narrative checkpoint, focused repair decisions, and progress-based stopping. Native and scripted verification pass. Fresh live Attention runs did not produce an approved Overview: Gemini and DeepSeek remained over height, Luna stopped on an unchanged invalid repair, and GLM exceeded the diagnostic deadline during planning. These are provider-output failures, not evidence that the production path is accepted across models. See `docs/verification/2026-09-12-overview-efficiency-implementation.md`.
Bibliography filtering is implemented in the AI evidence view, including downstream lookup and review. It invalidates older reading caches, excludes potentially contaminated older Overview references from Blog context, and preserves the complete retained paper. PDF filtering handles partial pages and explicitly headed appendices, as well as figure supplements after references. Unmarked lists and unusual PDF extraction order remain limits. The bundled paper's XHTML reference entries are excluded, and its PDF visualization pages after the references are preserved. See `docs/verification/2026-09-12-structured-overview-and-reading.md` for verification and scope.

Architecture narration operates at two levels: each selected module has an input, transformation and output, and visible transitions explain how those modules build into the proposed architecture. Planning, authoring, repair and review share this requirement. Existing panel titles and captions carry the bridges within the same page budget; no new layout primitive is needed. A teaching sequence must not imply an incorrect data-flow edge. The user requested implementation without further prototype rounds.
